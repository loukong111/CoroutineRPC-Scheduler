# 面试讲解提纲

这份文档用于快速准备项目讲解，重点不是罗列功能，而是说明为什么这么设计、解决了什么后端问题，以及还能如何继续演进。

## 一句话介绍

CorpCron 是一个基于 C++20 协程和 epoll 的轻量级 RPC 框架，并在其上实现了一个支持多节点部署的分布式定时任务调度系统。项目覆盖网络通信、协议设计、任务持久化、服务发现、分布式锁、失败重试、工程部署、自动化测试和 Qt 可视化管理端。

## 核心链路

1. 客户端通过自定义二进制 RPC 协议发送请求。
2. TCP 服务端基于 epoll 监听连接，并用协程封装异步读写。
3. 协议层完成包长校验、半包处理、Protobuf 反序列化和错误码封装。
4. `RpcDispatcher` 根据 `serial_id` 路由到 Echo、SubmitTask、CancelTask、ListTasks 等业务处理。
5. 定时任务写入 MySQL，调度器按 `next_run_at` 扫描到期任务。
6. 多节点通过 Redis 服务发现找到可执行节点，并使用 Redis 分布式锁保证同一任务只被一个节点执行。
7. 执行结果写入 `task_history`，失败任务按指数退避重试，超过上限后禁用。

## 关键设计点

### 为什么用 epoll + 协程

epoll 负责高并发连接的事件通知，协程把异步读写封装成接近同步的写法，避免大量回调嵌套。这样既保留 Reactor 模型的性能特征，也让业务代码更容易阅读和维护。

### 为什么自定义 RPC 协议

项目使用固定协议头保存 payload 长度和序列化类型，再配合 Protobuf 编解码业务消息。协议层统一处理半包、包长上限、未知方法、坏 payload 和统一错误响应，能够展示对网络边界和异常输入的防御意识。

### 为什么用 `next_run_at`

调度器不在内存里维护所有任务的倒计时，而是把下一次执行时间持久化到 MySQL。这样服务重启后可以恢复调度状态，多节点也能基于同一份任务表协同工作。

### Redis 锁为什么要校验 owner

释放锁和续约锁都必须校验 owner，避免节点 A 的锁过期后被节点 B 抢到，节点 A 又误删节点 B 的锁。这是分布式锁里最容易被问到的安全细节。

### 为什么需要 misfire 和重试退避

服务短暂不可用或节点重启后，任务可能错过原定时间。misfire 策略决定是否补跑或跳过；失败重试使用指数退避，避免故障期间频繁重试把系统打满。

## 工程化能力

- CMake 抽出 `corpcron_core`，服务端、工具和测试复用同一套核心代码。
- 提供 `.clang-format` 和 `.clang-tidy` 配置。
- `scripts/check.sh` 支持一键配置、构建、测试，以及可选格式检查、Docker 依赖启动和集成测试。
- Docker Compose 提供 Redis/MySQL 开发环境。
- Dockerfile 和 systemd unit 覆盖容器化和 Linux 服务化部署方式。
- CTest 覆盖协议、RPC 客户端、RPC 路由、Redis/MySQL 集成和端到端调度链路。

## 可以主动讲的难点

- 协程对象生命周期：`Task` 需要明确所有权，避免临时对象析构导致协程句柄被提前销毁。
- 协议安全：必须限制最大帧大小，否则恶意包长可能造成内存压力。
- 连接生命周期：服务退出时要停止调度器、关闭 TCP 服务、注销 Redis 服务并等待心跳线程退出。
- 多节点调度：锁续约和 owner 校验保证长任务执行期间不会被其他节点重复执行。
- 时区一致性：服务端和 MySQL 会话使用一致时区，避免 `next_run_at` 和查询 `NOW()` 出现偏差。
- 故障恢复：MySQL 操作前会确认连接状态，Redis 命令失败后会重连并重试一次，降低短暂网络抖动带来的任务中断概率。
- 超时控制：调度器通过 `scheduler.task_timeout_ms` 控制远程任务 RPC 调用耗时，避免任务长期占用线程池工作线程。
- 可观测性：服务端为每个 RPC 帧生成 `request_id`，日志中记录请求和响应协议号；运行指标可通过 `GetMetrics` RPC 查询，包括请求数、错误数、连接数、字节数、任务成功失败数、锁竞争结果和最大任务耗时。

## 当前边界

- RPC 鉴权是演示级 token，不等价于生产级身份认证。
- RPC 客户端支持同一连接连续发送请求，但还没有做连接池、负载均衡和失败节点熔断。
- Redis/MySQL 客户端目前是基础封装，已经支持简单重连；生产环境还需要连接池、更细的超时控制和更完整的错误分类。
- 当前指标存放在进程内，适合演示和单机观测；生产环境可进一步接 Prometheus/OpenTelemetry。
- 调度执行 handler 目前以演示任务为主，真实生产系统通常会接入任务沙箱、任务超时和更细的权限隔离。
- Qt 客户端用于项目演示和管理，不是互联网生产控制台。

## 面试回答模板

如果面试官问“这个项目最大的亮点是什么”，可以回答：

> 我不是只写了一个定时任务 CRUD，而是从网络框架开始做了一套完整链路：epoll + 协程封装网络 IO，自定义 RPC 协议处理半包和错误码，任务侧用 MySQL 持久化 `next_run_at`，多节点通过 Redis 服务发现和分布式锁保证单节点执行。同时我补了 Docker/systemd、自动化测试、压测脚本和 Qt 管理端，所以它更接近一个可演示、可部署、可验证的后端项目。

如果面试官问“还可以怎么优化”，可以回答：

> 下一步我会优先做三件事：第一是 Redis/MySQL 客户端增加连接池；第二是任务执行增加更细粒度状态机和取消语义；第三是完善压测和监控指标，比如连接数、任务延迟、锁竞争次数、执行成功率和 P99 延迟。
