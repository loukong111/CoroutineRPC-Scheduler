# 项目讲解提纲

这份文档用于快速讲清项目的主链路和设计取舍。重点不是罗列功能，而是说明为什么这么设计、解决了什么后端问题，以及后续还能如何演进。

## 一句话介绍

CorpCron 是一个基于 C++20 协程和 epoll 的轻量级 RPC 框架，并在其上实现了一个支持多节点部署的分布式定时任务调度系统。项目覆盖网络通信、协议设计、任务持久化、服务发现、分布式锁、失败重试、工程部署、自动化测试和 Qt 可视化管理端。

## 核心链路

1. 客户端通过自定义二进制 RPC 协议发送请求。
2. TCP 服务端基于 epoll 监听连接，并用协程封装异步读写。
3. 协议层完成包长校验、半包处理、Protobuf 反序列化和错误码封装。
4. `RpcDispatcher` 根据 `serial_id` 路由到 Echo、SubmitTask、CancelTask、ListTasks 等业务处理。
5. 定时任务写入 MySQL，调度器按 `next_run_at` 扫描到期任务，并用 `execution_id` 将任务从 scheduled 推进到 running。
6. 多节点通过 Redis 服务发现找到可执行节点，调度器使用 RPC 连接池和 round-robin 分发执行，并用 Redis 分布式锁保证同一任务只被一个节点执行。
7. 执行结果按 `execution_id` 幂等写入 `task_history`，失败任务按指数退避重试，超过上限后禁用。

## 关键设计点

### 为什么用 epoll + 协程

epoll 负责高并发连接的事件通知，协程把异步读写封装成接近同步的写法，避免大量回调嵌套。这样既保留 Reactor 模型的性能特征，也让业务代码更容易阅读和维护。

### 为什么自定义 RPC 协议

项目使用固定协议头保存 payload 长度和序列化类型，再配合 Protobuf 编解码业务消息。协议层统一处理半包、包长上限、未知方法、坏 payload 和统一错误响应，能够展示对网络边界和异常输入的防御意识。

### 为什么用 `next_run_at`

调度器不在内存里维护所有任务的倒计时，而是把下一次执行时间持久化到 MySQL。这样服务重启后可以恢复调度状态，多节点也能基于同一份任务表协同工作。

### Redis 锁为什么要校验 owner

释放锁和续约锁都必须校验 owner，避免节点 A 的锁过期后被节点 B 抢到，节点 A 又误删节点 B 的锁。这是分布式锁里最容易被问到的安全细节。

### 为什么需要 misfire 和重试退避

服务短暂不可用或节点重启后，任务可能错过原定时间。misfire 策略决定是否补跑或跳过；失败重试使用指数退避，避免故障期间频繁重试把系统打满。

## 工程化能力

- CMake 抽出 `corpcron_core`，服务端、工具和测试复用同一套核心代码。
- 提供 `.clang-format` 和 `.clang-tidy` 配置。
- `scripts/check.sh` 支持一键配置、构建、测试，以及可选格式检查、Docker 依赖启动和集成测试。
- Docker Compose 提供 Redis/MySQL 开发环境。
- Dockerfile、systemd unit、生产配置样例和 Nginx TLS 代理模板覆盖容器化、Linux 服务化和公网入口加固部署方式。
- Prometheus、Alertmanager 和 Grafana 示例覆盖长期指标采集、告警规则和可视化面板。
- CTest 覆盖协议、RPC 客户端、RPC 路由、Redis/MySQL 集成和端到端调度链路。

## 可以主动讲的难点

- 协程对象生命周期：`Task` 需要明确所有权，避免临时对象析构导致协程句柄被提前销毁。
- 协议安全：必须限制最大帧大小，否则恶意包长可能造成内存压力。
- 连接生命周期：服务退出时要停止调度器、关闭 TCP 服务、注销 Redis 服务并等待心跳线程退出。
- 多节点调度：锁续约和 owner 校验保证长任务执行期间不会被其他节点重复执行。
- RPC 客户端池：调度侧复用到各 endpoint 的长连接，并对连续失败节点做短暂冷却。
- 状态机幂等：任务执行前 CAS 标记为 running，完成时用 `execution_id` 校验，避免取消或重复执行时覆盖状态。
- 时区一致性：服务端和 MySQL 会话使用一致时区，避免 `next_run_at` 和查询 `NOW()` 出现偏差。
- 故障恢复：Redis/MySQL 客户端支持连接池、连接/读写超时和错误分类；MySQL 操作前会确认连接状态，Redis 命令失败后会重连并重试一次，降低短暂网络抖动带来的任务中断概率。
- 超时控制：调度器通过 `scheduler.task_timeout_ms` 控制远程任务 RPC 调用耗时，避免任务长期占用线程池工作线程。
- 可观测性：服务端为每个 RPC 帧生成 `request_id`，关键日志使用 `event="..." key="value"` 格式记录请求、响应、连接和调度执行；运行指标可通过 `GetMetrics` RPC、HTTP `/metrics` 或 Grafana 查询，包括请求数、错误数、连接数、字节数、任务成功失败数、锁竞争结果、任务执行耗时 p95/p99 和调度延迟 p95/p99；`/alerts` 和 Alertmanager 规则会基于这些指标给出失败告警状态。

## 当前边界

- RPC 鉴权是基础 token，不等价于生产级身份认证；公网入口建议通过 Nginx stream 做 TLS 终止，并结合防火墙限制后端端口。
- RPC 客户端池支持连接复用、round-robin 和失败节点短暂冷却；还没有实现加权负载均衡和熔断半开探测。
- Redis/MySQL 客户端已经支持连接池、简单重连、超时配置和错误分类；生产环境还可以继续补熔断、慢查询统计和更细的故障注入测试。
- 项目提供 Prometheus/Alertmanager/Grafana 本地示例；生产环境还需要补真实通知渠道、权限控制、数据保留策略和更完整的 OpenTelemetry 链路追踪。
- 调度执行 handler 目前以演示任务为主，真实生产系统通常会接入任务沙箱、任务超时和更细的权限隔离。
- Qt 客户端用于项目演示和管理，不是互联网生产控制台。

## 常见问题回答模板

如果有人问“这个项目最大的亮点是什么”，可以回答：

> 我不是只写了一个定时任务 CRUD，而是从网络框架开始做了一套完整链路：epoll + 协程封装网络 IO，自定义 RPC 协议处理半包和错误码，任务侧用 MySQL 持久化 `next_run_at`，多节点通过 Redis 服务发现、RPC 连接池和分布式锁保证单节点执行。同时我补了 Docker/systemd、自动化测试、压测脚本和 Qt 管理端，所以它更接近一个可演示、可部署、可验证的后端项目。

如果有人问“还可以怎么优化”，可以回答：

> 下一步我会继续补熔断半开探测、慢查询统计和故障注入测试，把存储抖动、坏节点恢复和任务执行隔离这几类生产问题验证得更充分。
